# JVM 内存与 GC 八股 · Track 设计规格

> 状态：设计稿（未开工）· 对应平台契约见 [`_CONTRACT.md`](./_CONTRACT.md)
> 一句话定位：给「背得出 GC 分代、却从没亲眼见过 OOM」的 Java 后端——在一个**故意会跑挂**的服务里，
> 把三类 OOM、类加载器泄漏、对象生命周期都用**本机可复现、可断言的证据**走一遍。

## 0. 一页纸摘要

| 项 | 值 |
|---|---|
| track.id | `jvm-bagu` |
| 骨架仓名 | `jvm-lab`（`manifest.skeleton_repo: "."`，仓根即骨架仓，同 `seckill-lab`） |
| 目标岗位 / 面试方向 | Java 后端 3~5 年：JVM 内存区域 / OOM 排查 / GC 日志 / 类加载 / JIT 是**每场必问**，且是最容易「背了也讲不出证据」的一块 |
| 语言栈 | Java 17（HotSpot）+ Maven 3.9 + JUnit 5（surefire `@Tag` 分组）+ `java.lang.management` MXBean |
| 基础设施 | **无外部依赖、无 docker**：纯进程内 + `ProcessBuilder` 起子 JVM；不联网、不下载任何 jar/agent |
| stage 数 | 6 个（其中 Stage 6 是**选修**；`stage-00-onboarding` 是 board-only，不出 ticket） |
| 依赖前置 | `manifest.requires: {java: "17", build: maven}`（不声明 docker：本 Track 不需要基础设施） |
| 与 database-bagu 的关系 | **互补不重叠**：那条练「数据落在磁盘上的正确性」（事务/锁/MVCC/缓存），这条练「数据停在内存里的形状」（堆/元空间/直接内存/类/对象）。两条共用同一套骨架仓约定与分支链契约，但不共用代码 |
| 预计落地工作量 | 骨架 ≈ 6 人日 · canonical 测试与 helper ≈ 8 人日 · 题面与判据 ≈ 3 人日 · 分支与 digest pin ≈ 1 人日（详见 §7） |

**卖点（三条以内）**

1. **OOM 是做成「必然」的，不是碰运气**：子 JVM 一律用**固定的 `-Xmx`/`-XX:MaxMetaspaceSize`/`-XX:MaxDirectMemorySize`**
   起，工作负载与对象大小也是固定的——「这把一定炸」由算术保证，跟机器快慢无关。
2. **判据是可观测结构，不是毫秒数**：GC 停顿的毫秒、JIT 生效的时机、吞吐百分比**一律不进 canonical 测试**；
   进测试的是「GC 日志里出现了哪类停顿」「某个类加载器有没有被卸载」「堆转储里某类的实例数是否超过界」。
3. **每一步都有对照实验**：同一份代码在「开着 vs 关着某个 JVM 开关」下的**结构差异**就是判据，
   学员交卷时手里天然有一组 before/after 证据，而不是一句「我加了个参数」。

## 1. 判据可行性论证（最重要的一节）

### 1.1 总原则：本 Track 的判据长什么样

本 Track 不判「快不快」，只判三种**结构事实**，每一种都在学员本机离线可得：

| 判据形态 | 怎么拿 | 为什么不怕抖动 |
|---|---|---|
| **进程级结局**：子 JVM 是「跑完了并打出收尾标记」还是「带着某类 OOM 死了」 | canonical 测试用 `ProcessBuilder` 起子 JVM，读退出码 + 子进程自己写出的结构化 stdout 标记 | 结局是二值的；OOM 由固定内存上限 + 固定存活集算术保证，不靠时序 |
| **JVM 自带计数器/MXBean**：已加载类数（`ClassLoadingMXBean`）、池内缓冲区总容量（`BufferPoolMXBean`）、堆/元空间 used（`MemoryMXBean` + `MemoryPoolMXBean`） | 子 JVM 自己在关键点采样并打印；需要时先 `System.gc()` 再用**有界轮询**读 | 计数器是单调量或退出前的稳态量，与墙上时间无关 |
| **GC 日志的结构**（不是时长） | `-Xlog:gc*:file=...`，测试按行做正则：出现的是 `Pause Young` 还是 `Pause Full`、有没有 `[gc,phases]`、行格式是否可解析 | 只匹配「事件类型与格式」，不匹配任何毫秒/字节数值 |

> [!IMPORTANT]
> 「固定参数让结论稳定」是本 Track 的**唯一**确定性来源。所有 canonical 测试都通过一个受保护的
> 测试 helper 起子 JVM，参数来自一个**受保护的、进判定面的固定参数文件**（`src/test/resources/jvmflags/*.flags`）。
> 学员改不到它，平台体检时也不必信任学员机器上的默认 GC/堆配置。

### 1.2 逐 stage：骨架红在哪、为什么红在业务缺陷上

| stage | 骨架初始（红） | 红在哪个业务缺陷上 | 参考解（绿） |
|---|---|---|---|
| 1 堆 OOM 与堆转储 | `HeapOomAcceptanceTest.shouldSurviveFixedBudgetRun` 失败：子 JVM 在 `-Xmx256m` 下跑完固定批次后，**最后一次固定大小的收尾分配**拿到 `OutOfMemoryError: Java heap space`，子进程打出 `GATE=no-headroom` 与 `OOM=java.lang.OutOfMemoryError: Java heap space` | `BufferPool` 把每批快照 `add` 进一个**静态、永不清理**的列表：存活集随记录数单调增长，与 GC 多努力无关 | 同一份负载、同一个 `-Xmx`，子 JVM 跑到 `GATE=headroom-ok`，收尾预算分配成功，`PROCESSED=100000` 与固定批次总数一致，且不产生 OOM |
| 2 Metaspace OOM 与类卸载 | `MetaspaceAcceptanceTest.shouldKeepMetaspaceBounded` 失败：子 JVM 在 `-XX:MaxMetaspaceSize=64m` 下处理固定批次的动态规则，要么在 `LOADED_RULES` 未达总数前就以 `OutOfMemoryError: Metaspace` 结束，要么结束时 `METASPACE_AFTER_GC` 明显高于固定上界 | `RuleClassFactory` 的每次编译都新建一个 `ClassLoader` 并把它留在缓存/列表里：**不同类名的类元数据只增不减**，元空间里没有任何东西可回收 | `LOADED_RULES` 等于请求总数、`METASPACE_AFTER_GC` 落在固定上界（16MB）以内，且**同一份规则的重复编译不再产生新类** |
| 3 直接内存 OOM 与缓冲区池 | `DirectMemoryAcceptanceTest.shouldReleaseBuffersAfterUse` 失败：子 JVM 在 `-XX:MaxDirectMemorySize=64m` 下把固定条数记录灌进缓冲区池后抛 `OutOfMemoryError: Cannot reserve ... bytes of direct buffer memory`（子进程打出 `OOM=...`），`POOL_CAPACITY_AFTER_CLOSE` 根本来不及打 | `DirectMemoryPool` 只分配、不释放：`ByteBuffer` 的 Cleaner 只在 GC 时被调度，而堆里毫无压力（GC 根本不需要跑），于是直接内存一直挂着 | 同一份负载灌完不抛 OOM，显式收尾后 `POOL_COUNT=0` 且 `POOL_CAPACITY_AFTER_CLOSE=0`，运行期 `POOL_PEAK_CAPACITY` 落在固定上界（32MB）以内 |
| 4 类加载与双亲委派 | `ClassLoadingAcceptanceTest.shouldUnloadClassLoaderAfterRelease` 失败：子 JVM 建固定批次的「规则类加载器」，丢弃引用并做有界 GC 后，`CLASSES_AFTER_GC` 仍显著高于固定上界——**一个都没卸载** | `RuleLoaderLab` 用 `Thread.currentThread().getContextClassLoader()` 当父加载器**打破委派**，再把每个 loader 留在自己的静态 map 里：loader 活着 ⇒ 它定义的类不能卸载 | `CLASSES_AFTER_GC` 落到固定上界以内（loader 被回收、类被卸载），同时 `RULES_VERIFIED=400` 证明该被加载的规则仍然加载正确、没有被委派改成父加载器里的另一个同名类 |
| 5 对象生命周期与逃逸分析 | `EscapeAnalysisAcceptanceTest.shouldEliminateShortLivedAllocations` 失败：同一份 30 万次循环的负载，`-XX:+DoEscapeAnalysis` 与 `-XX:-DoEscapeAnalysis` 两次运行 **`PEAK_HEAP_USED_AFTER_GC` 几乎一样高**（都超过固定上界） | `BufferPool.record` 把每次新建的 `OrderSnapshot` 交给 `ProfileRecorder.record(...)` 留档 → 对象**逃逸**出方法，标量替换不可能发生 | 开着逃逸分析那一次 `PEAK_HEAP_USED_AFTER_GC` 落在固定上界以内，关掉那次仍高；两次 `CYCLES` 相同（功能等价），差值纯粹来自对象是否被消除 |
| 6（选修）堆转储实战诊断 | `HeapDumpDiagnosisAcceptanceTest.shouldMatchFixtureDump` 失败：`docs/diagnosis/stage06-diagnosis.txt` 在骨架里存在，但**每个取值都还是模板占位符**，解析不出可用值 | 学员还没做过真实堆转储分析——这是**证据交付**类红（骨架提供字段契约，值由学员填），不是代码红 | 交付文件填的「数量第一名 / 占用第一名」两组类名、实例数与浅堆大小，与 canonical 测试**当场从固定 dump 解析出来的真值**在容差内一致 |

**红为什么「红在对的地方」**（这一条是判别性门的核心，逐条排除常见的「假红」）：

- **不是编译错**：六个缺陷文件在骨架上都编译通过、`ProfileService` 的正常路径（记录入队 → 处理 → 汇总）能跑通，
  红的全部是**资源上限撞墙**或**证据缺失**。
- **不是脚本为空**：每个 canonical 测试都跑真实负载并断言子进程的结构化输出，断言失败信息里带子进程原始 stdout/stderr。
- **不是装配失败**：本 Track 没有外部基础设施，没有 Spring 上下文、没有端口、没有镜像——「环境没起来」这种红在物理上不可能。
- **不是永远红**：`stage-NN-<name>-sol` 分支上六个 stage 全绿（准入门的另一半就是这样验的）。
- **红在缺陷的因果链上**：每一条红都能一句话说清「因为 X 保留了不该保留的引用 ⇒ 固定上限 Y 被撞穿」。
  参数不是判据，**接线才是判据**——学员把 `-Xmx` 调大也不会变绿，因为子 JVM 的参数是受保护的固定文件。

### 1.3 确定性论证（为什么多次跑结果一致）

1. **上限固定**：堆 / 元空间 / 直接内存三个上限都写死在受保护的 `.flags` 文件里，不由学员机器决定。
2. **工作负载固定**：每条负载的条数、每条记录的对象大小都是常量（如 100000 条 × 4096B 的 `byte[]`），
   于是「存活集最小可能值」是一个能算出来的常数。
3. **结论由算术保证**：只要「存活集最小可能值 > 上限 − 启动开销 − GC 余量」，OOM 就必然发生；
   反过来，修复后「存活集上界 + 收尾预算 < 上限」也必然成立。两侧都留了 ≥2 倍余量。
4. **子进程自述状态**：结论不靠解析易变的 stderr 文案，而靠子 JVM 自己打印的 `KEY=VALUE` 标记
   （`GATE=`、`OOM=`、`PROCESSED=`、`CLASSES_AFTER_GC=`、`POOL_CAPACITY_AFTER_CLOSE=`……）；
   即便日后 JDK 补丁改了 OOM 文案，测试也只把文案当**补充证据**，判定仍落在标记上。
5. **类卸载用有界重试**：`System.gc()` + 轮询 `ClassLoadingMXBean`（上限 10 次 / 每次 200ms），
   而不是依赖「某一刻恰好卸载了」；轮询次数的目的是把 flaky 概率压到可控，不构成时间阈值判据。
6. **JDK 一致性前置断言**：每个 canonical 测试开头断言「本机 `java.version` 主版本 = 17 且
   `java.vm.name` 含 HotSpot」，不满足就**响亮失败**并提示去看 `docs/架构与约定.md` 的版本约定——
   宁可说「环境不可判定」，也不给一个静默通过的绿。
7. **把「编译层级」这个自由度关掉**：所有子 JVM 的 `.flags` 里都写死 `-XX:-TieredCompilation`
   （只留 C1/C2 的确定一档），因为分层编译的层数取决于编译线程数与机器核数，
   会让 Stage 5 那种「对照差」在快机器和慢机器上落在不同的数量级上。这一条是本 Track 里
   「怎么把抖动量确定化」最实在的一招：**不是把阈值放宽，而是把产生差异的自由度删掉**。

### 1.4 不可判定或需要妥协的考点（诚实记账，不要藏）

| 考点 | 为什么不能当判据 | 规格里的处置 |
|---|---|---|
| **GC 停顿的毫秒数**（`Pause Young (Normal) ... 12.345ms`） | 同一台机器上相邻两次都能差一个数量级；受 CPU 频率、邻居进程、内核调度影响 | **降级为可观测**：只看日志里**出现了哪类停顿**，并在 `expect` 里说明「毫秒数只用来给学员自己看趋势」。绝不写进断言 |
| **吞吐量 / GC 时间占比 / 默认 `-XX:MaxGCPauseMillis` 是否达成** | 同上，且与工作负载的分配速率强耦合 | 不进判据；只在八股地图的「面试题」列里作为**口试题**出现 |
| **G1 与 Parallel「谁更快」** | 小堆下结论随堆大小反转，属于参数敏感性而非结构事实 | 只做**结构对比**：同负载下 Parallel 出现若干次 `Pause Full` 而 G1 一次都没有（因为存活集被修好之后，G1 无需 full compaction）；「谁快」写成讨论题 |
| **JIT 编译发生的时机 / 编译次数 / OSR 与否** | 与机器核数、编译线程抢占、热点阈值相关，`-XX:+PrintCompilation` 的输出不保证可复现 | **降级为可观测**：`PrintCompilation` 日志只作为学员自己读的「证据读物」，测试不解析它；判据改用**分配压力/堆高的结构差**（见 Stage 5） |
| **逃逸分析、标量替换、锁消除的内部判定结果** | 属于 C2 内部决策，没有稳定的外部可观测接口（旧版 `-XX:+PrintEliminateAllocations` 在 JDK 17 上已不可用/不稳定） | 用**对照实验**：同一份代码开/关 `-XX:+DoEscapeAnalysis` 两次运行的堆高结构差。锁消除**不进 spec**（本 Track 不讲锁，见 §2 边界） |
| **对象晋升年龄、`tenuring threshold` 的实际取值** | 与 GC 实现细节和幸存区大小耦合，日志字段在不同更新版本间会变 | 不进判据；只在八股地图里作为面试题 |
| **绝对内存占用 / 镜像大小 / RSS** | 与 JDK 发行版、是否启用 CDS、操作系统页大小有关 | 只在 `expect` 里作为「学员自己可比对的第二证据」出现，不进断言 |
| **具体 JDK 补丁版本下 Metaspace 单类元数据大小** | 会随版本变化 ⇒ 「多少类刚好撑爆」不是稳定常数 | 判据只要求「元空间在固定批次内**保持有界**」与「请求的类都加载到了」，不要求精确的类数上限 |
| **`jhat`** | JDK 9 起已从 JDK 移除（要另装旧版）；`MAT` 需要人工下载 | 作为**选修**「自己动手看一眼」的手段写进 H2/H3；canonical 判据自带一个最小 HPROF 解析器，不依赖任何外部工具（详见 §6 供应链注意） |

## 2. 骨架仓设计

### 2.1 边界声明（先划清，避免两条 Track 重叠）

本 Track 只讲**内存与 GC**：

- ✅ 讲：堆 / 元空间 / 直接内存三个区域、OOM 三类、堆转储、GC 日志结构、类加载与卸载、对象生命周期（逃逸/标量替换）。
- ❌ **不讲**（归 `concurrency-lab`）：JMM、`volatile`、`synchronized` 与锁消除、`happens-before`、线程池、
  `ThreadLocal` 语义、CAS/原子类。骨架里**故意不出现**任何并发原语，免得两条 Track 的考点互相串味。
  （Stage 5 的对照实验只用单线程循环与 JVM 开关，不引入任何锁或内存序问题。）
- **Stage 5 为什么在边界内**：它讲的是「对象的分配与消除」——分配压力直接决定新生代回收频率，
  是本 Track 主线的收尾（一个对象活多久、要不要上堆）。它**只**做逃逸分析/标量替换这一件事，
  观察手段也限定在「堆的存活集形状」，不碰编译器的 IR、也不碰锁。若评审认为 JIT 面太宽，
  裁掉整条 Stage 5 是安全的：它是链尾前的选修性延伸（Stage 6 用不到它的结论），
  但**不要**把它拆成"锁消除/编译优化"混进别的阶段——那正是这两条 Track 会重叠的地方。

### 2.3 分层与约定

- **没有 Spring、没有容器、没有数据库**。`JvmLabApplication.main(args[0])` 按负载名跑一段固定工作，
  `System.exit(0)` 正常收尾；任何 OOM 都在 `main` 的兜底里被**捕获 + 落成标记 + 退出**，
  这样「OOM」本身变成一条可断言的 stdout 记录，而不是一段易变的 stderr 文案。
- **待机记录（emergency record）**：`main` 启动时预分配一小块 `byte[]` 和一个预格式化的行缓冲，
  OOM 处理器只用这块内存把标记写进 `FileDescriptor.err` 再 flush——元空间耗尽时堆是空的，
  这个设计让「濒死打印」几乎不可能失败，判据因此稳定。
- **负载参数集中**：条数、每条的 payload 大小、循环次数全在 `jvmlab.properties` 里，代码只读它。
  这样「OOM 的算术」是文档化的常数，而不是散落在代码里的魔数。
- **`pom.xml` 的 surefire 必须写成确定形态**：`forkCount=1`、`reuseForks=false`、
  `parallel` 关闭、`argLine` 为空（**不要**在 surefire 的 JVM 上设堆上限——那会让「测试自己也需要内存」
  与「被测子 JVM 的上限」两件事混在一起），`-Dfile.encoding=UTF-8`、`-Duser.language=zh -Duser.country=CN`。
  子 JVM 的内存参数**只**来自 `.flags` 文件，测试 JVM 的参数不参与任何判据。
- **JVM 参数集中**：所有子 JVM 参数都在 `src/test/resources/jvmflags/*.flags` 里，`JvmRunner` 逐行读取并与
  `JvmFlags` 里的白名单求交——**学员无法在执行期改上限**，他只能改接线。
- **`HprofReader` 是「最小可用」的**：只解析 HPROF 的 `UTF8` / `LOAD_CLASS` / `STRING` / `INSTANCE_DUMP`
  四类记录，产出「类名 → 实例数 / 浅堆字节」。它**不做**支配树与 retained size，
  所以 Stage 6 的判据用「实例数 + 浅堆」这两个它真能给准的量（见 §1.4）。

    「你不再使用这个规则对象」而消失——只有定义它的那套东西能被回收，它才可能被卸载。

## Stage 1 · 堆 OOM 与堆转储 ⬜

**亲手场景**：巡检服务的快照被静态名单一直持有 → 你让固定额度下再也分不出新对象 → 你读堆转储定位持有者。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 运行时内存区域 | 堆(线程共享,对象)/虚拟机栈(私有,栈帧)/元空间(类元数据)/直接内存(NIO) | JVM 运行时数据区都有哪些？哪些线程共享？ |
| 可达性分析 | 从 GC Roots 出发可达即存活；GC Roots 含栈帧局部变量、静态字段、常量、JNI 引用 | 如何判断一个对象可以被回收？为什么不用引用计数？ |
| 分代假设 | 绝大多数对象朝生夕灭 ⇒ 新生代频繁小回收、老年代少见整体回收 | 为什么分代？对象什么时候进老年代？ |
| 分配与 OOM 的关系 | 分配失败前先触发回收；回收后仍不够才抛 OOM ⇒ 「GC 很勤」与「内存不够」可以同时成立 | 为什么 Full GC 频繁不代表 GC 有问题？ |
| 堆转储 | `HeapDumpOnOutOfMemoryError` 或手动命令导出全部对象图，是「谁占着内存」的直接证据 | 线上怎么拿到并分析堆转储？ |
| 直方图 vs 堆转储 | 直方图只有类与数量/占用（轻），堆转储有引用路径（重） | jmap -histo 和 dump 各自什么时候用？ |

**复现命令**：
```bash
java -Xmx256m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=target/gc-evidence/ \
     -cp target/classes com.devteam.jvmlab.JvmLabApplication heap-oom
```

## Stage 2 · Metaspace OOM 与类卸载 ⬜

**亲手场景**：规则每编译一批就多留一套加载器 → 元数据只增不减 → 堆一直健康、进程照样死。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| Metaspace vs 永久代 | JDK 8 起类元数据移到本地内存的 Metaspace，默认不限但可设上限 | Metaspace 和永久代有什么区别？会 OOM 吗？ |
| 类元数据的归属 | 类的元数据挂在「定义它的类加载器」上，loader 存活则类不可卸载 | 一个类什么时候可以被卸载？ |
| 类卸载条件 | 该类所有实例已回收 + 定义它的 loader 已回收 + 对应的 Class 对象无引用 | 满足什么条件类才会被卸载？ |
| 运行期生成类 | 动态代理/字节码生成会持续产生新类，缓存键设计不当就会重复定义 | 动态代理为什么会把 Metaspace 撑爆？ |
| 溢出归宿 | 元数据不足抛 `OutOfMemoryError: Metaspace`，堆转储里看不到原因 | 报 Metaspace OOM 该怎么查？ |

**复现命令**：
```bash
java -XX:MaxMetaspaceSize=64m -Xlog:class+load=info,class+unload=info:file=target/gc-evidence/classes.log \
     -cp target/classes com.devteam.jvmlab.JvmLabApplication metaspace
```

## Stage 3 · 直接内存 OOM 与缓冲区 ⬜

**亲手场景**：零拷贝转运的堆外缓冲区只借不还 → 堆指标全绿、容器被杀 → 你用池计数器把账算清。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 直接内存 | `allocateDirect` 在堆外分配，不在堆上限内，由 `MaxDirectMemorySize` 约束 | 直接内存属于 JVM 哪块区域？受哪个参数限制？ |
| Cleaner 回收时机 | 堆外内存由虚引用 + Cleaner 在 GC 时释放，堆无压力则迟迟不释放 | 直接内存什么时候释放？为什么它会泄漏？ |
| 失败信号 | 预留失败抛带「Cannot reserve」字样的 OOM，或进程被系统 OOM Killer 干掉 | 堆外内存溢出和进程被杀怎么区分？ |
| 可观测手段 | `BufferPoolMXBean` 按类型给出容量与已用，堆外池在 `MemoryPoolMXBean` 里单独一档 | 怎么监控堆外内存？ |
| 堆内存泄漏 vs 堆外泄漏 | 前者堆转储可查，后者要在池计数器与本机进程视角上看 | 堆没涨但内存一直涨，怎么排查？ |

```

## Stage 4 · 类加载与双亲委派 ⬜

**亲手场景**：热更新用自定义加载器却绕过了委派 → 同名类出现两份 + loader 被登记表握住 → 元数据不回落。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 类加载过程 | 加载 → 验证 → 准备 → 解析 → 初始化；`loadClass` 默认先委派父加载器 | 描述类的生命周期 |
| 双亲委派 | 先父后子，保证核心类不被替换、同名类只被定义一次 | 为什么需要双亲委派？怎么打破？ |
| 打破委派的场景 | SPI/模块化、热部署与隔离、字节码框架都需要绕过或改写委派 | 哪些框架打破了双亲委派？为什么？ |
| 类加载器泄漏 | 静态表、线程上下文、ThreadLocal 都会隐式持有 loader，进而钉住它定义的类 | 类加载器泄漏的典型原因？ |
| 类的唯一性 | 全限定名 + 定义它的加载器共同决定类的身份，「同名不同类」会引发 `ClassCastException` | 同一个类为什么会出现两份？ |

**复现命令**：
```bash
java -Xlog:class+load=info,class+unload=info:file=target/gc-evidence/reload.log \
     -cp target/classes com.devteam.jvmlab.JvmLabApplication classloader
```

## Stage 5 · 对象生命周期与逃逸分析 ⬜

**亲手场景**：校验上下文被交给留档模块 → 短命对象全都上堆 → 你把作用范围收回来，用对照实验证明差别。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 对象分配 | 优先在 TLAB 上分配；逃逸分析结论不同会改变分配与消除策略 | 对象一定分配在堆上吗？ |
| 逃逸分析 | 分析对象的作用范围（不逃逸/方法逃逸/线程逃逸），是后续优化的前提 | 逃逸分析在分析什么？ |
| 标量替换 | 不逃逸的对象可拆成字段直接放在栈/寄存器，省掉堆分配 | 什么是标量替换？什么条件下发生？ |
| 分配压力 | 分配速率决定新生代回收频率；消除短命对象能直接削弱分配压力 | 怎么降低 GC 频率？ |
| 可观测的边界 | 编译器内部决策没有稳定外部接口，只能靠对照实验与计数器间接观察 | 你怎么证明 JIT 优化生效了？ |

**复现命令**：
```bash
java -Xmx256m -XX:+DoEscapeAnalysis -cp target/classes \
     com.devteam.jvmlab.JvmLabApplication escape-on
java -Xmx256m -XX:-DoEscapeAnalysis -cp target/classes \
     com.devteam.jvmlab.JvmLabApplication escape-off
```

## Stage 6（选修）· 堆转储实战诊断 ⬜

**亲手场景**：只有一份别人留下的、没有崩溃现场的堆转储 → 你交出「数量第一名与占用第一名」两张表。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 转储读取 | HPROF 里 `LOAD_CLASS` + `INSTANCE_DUMP` 就能给出「类 → 实例数/浅堆」 | 堆转储里都有什么？ |
| 直方图口径 | 实例数与浅堆好算；保留集要支配树，口径差异大 | 浅堆、深堆、保留集分别是什么？ |
| 数量 vs 占用 | 「很多小对象」与「少数大对象」是两类不同的病，两张排序表要一起看 | 你排查内存问题先看哪个排序？ |
| 引用链 | 从 GC 根到对象的引用链回答「为什么它还活着」，是收尾动作而非第一步 | 怎么找内存泄漏的根源？ |
| 泄漏 vs 高水位 | 泄漏是单调不可回落的量，高水位是可回落但设得高 | 内存缓慢上涨一定是泄漏吗？ |
| 结论表达 | 诊断的产物是可核对的事实 + 排除依据，不是工具输出截图 | 复盘会上你怎么讲清内存问题？ |

**复现命令**：
```bash
./scripts/gen-heapdump.sh && ls -l target/gc-evidence/*.hprof
# 用自己的手段在这份转储上算出「类 → 实例数 / 浅堆」的排序
```

> [!NOTE]
> 与 `seckill-lab` 的差异要写清楚：那边 `digest_pin` 里的 `mysql:` / `redis:` 是**镜像**摘要；
> 本 Track **没有镜像**，所以那类条目不存在。"每个声明的 runtime 入口都有 `digest_pin`"
> 这条硬门只要求覆盖 `compose`/`build`/`tests`/`sim` 中被声明的那几个。

- **判定面逐条论证**（每一条都是「判据依赖它」或「拿它就能改判据」）：
  1. `./pom.xml` —— surefire 的 `forkCount`/`reuseForks`/`argLine`/依赖版本都在这里；改它可以把测试跳过、
     把子 JVM 参数注掉、或把断言库换掉。判据完全建立在「测试能跑起来」上，所以它必须在判定面里。
  2. `./scripts/` —— `build.sh`（准入门的构建入口）、`digest-pin.sh`（摘要生成）、
     `gen-heapdump.sh`（Stage 6 夹具的生产者）。改生成脚本就能改夹具 → 直接改判据。
  3. `./src/test/` —— canonical 测试本体 + helper（`JvmRunner`/`Evidence`/`JdkAssumptions`/`HprofReader`）
     + 固定参数文件 + 固定夹具。这是「判据本身」，也是本 Track 的唯一判断来源。
  4. `./src/main/java/com/devteam/jvmlab/config/` —— `JvmFlags` 读出并校验子 JVM 参数；改它就能让上限漂移。
  5. `./src/main/java/com/devteam/jvmlab/monitor/` —— 所有观测量的读数来源（堆/元空间/类数）；改它等于改判据的尺子。
  6. `./src/main/java/com/devteam/jvmlab/diag/` —— `DiagnosticTools` 的落盘路径与 `HprofReader` 的解析口径，
     改它就能让 Stage 6 的对照真值跟着动。
  7. `./src/main/resources/jvmlab.properties` —— 负载条数与对象大小是「OOM 必然发生」的算术前提，改它就是改判据。
  8. `./docs/JVM八股地图.md` —— 锚点契约（改了标题就要重算 `bagu_map_ref`）。
  9. `./docs/架构与约定.md` —— 固定约定（上限/日志/版本）的权威位置，题面里让学员读它，它就不该被改。
  - **刻意不放进判定面的**：`buffer/`、`rule/`、`nio/`、`profile/` 四个业务包与 `docs/diagnosis/`——
    它们是学员的改动面；D1 要求 `mentor_policy.may_write` 与它们不相交（本 Track 六张卡的 `may_write` 均为 `[]`）。
- **必须 pin 的东西**：`build.sh`、`src/test/**`、`src/test/java/.../base/**`（**子 JVM 参数的读取器**，
  它一变全部结论都可能漂）、`src/test/resources/jvmflags/**`（上限与开关）、`scripts/gen-heapdump.sh` +
  固定夹具、以及 `HprofReader`（解析口径）。**本 Track 没有镜像**，所以 `digest_pin` 里没有 `mysql:`/`redis:`
  这类条目——硬门要求的是「**声明了的** runtime 入口（compose/build/tests/sim）都有摘要」，
  不是「必须有镜像摘要」。摘要由 `scripts/digest-pin.sh` 生成；改动上述任一文件后重跑它，
  并同步 `ticket.grader.correctness.canonical_test`。
- **供应链注意**：本 Track **不引入任何第三方二进制、镜像或网络依赖**。子 JVM 只用本机 JDK；
  GC 日志、堆转储、类直方图全部由 JDK 自带能力产生；Stage 6 的 HPROF 解析器是本仓自己的最小实现，
  刻意**不引入 MAT 之类的重依赖**（它需要人工下载，违反 D3「学员本地离线可复现」）。
  唯一"会执行的东西"是 `mvn test` 与 `scripts/*.sh`，两者都在判定面里被 digest 锁定。
  学员机器上会被起的进程只有两个：surefire 自己的 JVM，以及它 fork 出来的子 JVM——**没有守护进程、没有网络端口**。
- **trust_level 建议**：`self`（自托管、自写）。升 `verified` 需要 `contribute.review.signed_by` 至少一名维护者背书
  + `digest_pin` 全量锁定 + 过 CI 准入；本 Track 的额外门槛建议是「六条 `-sol` 分支全绿」的证据报告。
- **版本漂移的现实**：`digest-pin.sh` 输出的摘要是**本机生成**的。GC 日志在 JDK 更新版本之间出现过字段微调，
  所以摘要与「已实测的 JDK 发行版」应当一起记在 `docs/架构与约定.md` 里（同 `seckill-lab` 记录镜像摘要的做法）。

## 7. 风险、妥协与工作量

| 风险 | 影响 | 缓解 |
|---|---|---|
| **OOM 不必然**（负载量级不够、机器 JVM 启动开销差异） | Stage 1/2/3 的判别性门会变成 flaky，甚至「骨架也绿」 | 每个上限后的存活集都留 ≥2 倍余量；子进程用**固定参数文件**起；负载参数集中在一处便于调；准入校验必须在**同一台机器**上同时验骨架红与 `-sol` 绿 |
| **`HprofReader` 解析口径漂移**（不同 JDK 的 HPROF 记录微调） | Stage 1/6 的直方图断言失准 | 只解析四个稳定记录类型；判据用「实例数 + 浅堆」并给容差；每个 canonical 测试前置断言 JDK 主版本 |
| **共享 helper 改动破坏「只加不删」链** | 后续阶段分支合并时会引入非本阶段内容 | helper 在 Stage 1 一次性落地并冻结；任何 helper 改动都要重跑全部阶段判别性校验（列为发布前必做项） |
| **子进程挂死**（GC 抖动或死循环） | CI/本地跑测试可能长时间不返回 | `JvmRunner` 统一设置超时（120s）并在超时后强杀，超时**判定为失败**而非跳过 |
| **`jcmd`/`jmap` 在受限环境不可用** | Stage 1/2/4 的附加证据拿不到 | 判据的全部硬门都走 `ProcessBuilder` + stdout 标记 + MXBean，`jcmd`/`jmap` 只用于"人自己看"的证据；`DiagnosticTools` 拿不到就明确报「本机不可用」，绝不静默通过 |
| **Stage 5 与 JIT 实现细节强耦合** | 未来 JDK 改变逃逸分析行为会让判据失效 | 判据用「开/关开关的对照差」而不是绝对阈值；**子 JVM 一律加 `-XX:-TieredCompilation`（受保护的 `.flags` 里写死）**，让「编译层级」这个自由度消失，否则同一个断言会因为机器核数与编译线程抢占而不稳定；在 `docs/架构与约定.md` 里钉住已验证的 JDK 发行版；把该门标注为**最脆弱的一门** |
| **Stage 6 的「红」是交付物未填而不是代码红** | 平台的判别性门要求骨架红，若模板里预置了任何可用取值，这一关在骨架上就会绿 | 骨架只提交**字段名 + 占位符**；解析器把占位符判为「无可用取值」；把这一条写进 §1.2 与准入门自查，让人工评审也必须确认 |
| **Stage 6 的固定 dump 是二进制夹具** | 体积膨胀 + 生成环境差异 | 夹具由 `gen-heapdump.sh` 在本地生成，控制在 10~20MB；判据只看"类 → 实例数/浅堆"这类稳定字段；生成环境写进约定文档 |
| **选修阶段拉低整体完成率** | 学员卡在最后一关，前五关的收获被稀释 | Stage 6 在 `manifest.stages` 里正常列出，但题面明确写「选修」，`progression` 只依赖 Stage 5，不阻塞任何后续内容 |

**工作量拆解**（合计 ≈ 18 人日）：

- **骨架** ≈ 6 人日：五个业务包 + 三块 monitor/diag + 一个负载分发 `main` + `pom.xml`/`build.sh`/`digest-pin.sh`。
  其中 `HprofReader`（最小 HPROF 解析）与 `JvmRunner`（子 JVM 控制）各占约 1 人日，是硬骨头。
- **canonical 测试** ≈ 8 人日：六个测试类 + helper + 六个 `.flags` 文件 + 一个 dump 夹具。
  最贵的是 Stage 5（对照实验设计）与 Stage 6（真值重算）。
- **题面与判据** ≈ 3 人日：六张 ticket 按 `_CONTRACT.md` §3 的八块写全，并按 §3.1 复算六个锚点。
- **分支与 pin** ≈ 1 人日：12 条分支（6 base + 6 `-sol`）、`digest-pin.sh` 跑通、`paper validate-track` 全绿。

**建议的实施顺序**（按「判据最硬、最能验证契约」排序）：

1. **Stage 1**：先把「固定上限 ⇒ 必然 OOM ⇒ 可断言结局」这条方法论验通，它是另外五关的地基，
   也是唯一能一次性证明"本 Track 的判据站得住"的阶段。同时把 `JvmRunner`/`Evidence`/`JdkAssumptions` 冻结下来。
2. **Stage 3 或 Stage 4**：两者的判据都纯靠 JVM 计数器（池容量、已加载类数），不依赖任何解析器，
   是"低成本高确定性"的一关；先落一关能复用的范式，再看是否需要 `HprofReader`。
3. **Stage 2**：与 Stage 4 同源但更粗（批量 vs 生命周期），在 Stage 4 之后做更省事。
4. **Stage 5**：已知最脆弱的一门，等前面四关把 `JvmRunner` 的对照实验能力磨出来之后再做，并先做原型验证。
5. **Stage 6**：最后做，因为它复用 Stage 1 的转储能力 + 自己的解析器，且是选修，可以延后发布。

- [ ] 骨架可构建（`./scripts/build.sh` = `mvn -DskipTests compile` 成功）；**无 compose**，故"基础设施可起"自动满足
- [ ] 每个 stage：骨架红 / `-sol` 绿，且红在业务缺陷（Stage 6 红在**交付物未填**，已在 §1.2 显式说明）
- [ ] `files_to_change` 每个路径在骨架里存在（`BufferPool.java` / `RuleClassFactory.java` /
      `DirectMemoryPool.java` / `RuleLoaderLab.java` / `ProfileRecorder.java` /
      `docs/diagnosis/stage06-diagnosis.txt` 的角色在 §2.4 逐条列明；最后一个**必须以只有字段名的空模板**提交进骨架，
      否则要么过不了准入门（文件不存在），要么让 Stage 6 在骨架上就变绿——两种都是废稿）
- [ ] 八股锚点可解析（六条已逐个演算，见 §5 的锚点对照表；Stage 6 的全角括号标题优先复算）
- [ ] 题面 / concepts / hints 无解法行（六张卡的"泄漏自查"逐条说明）
- [ ] `protected_paths` 每条都能匹配到骨架里的东西（九条，见 §6 论证）
- [ ] `runtime` 每个**声明的入口**都有 `digest_pin`（`build`/`tests`/`sim` 三项；`runtime` 对象
      本身不得出现自定义键——schema 是 `additionalProperties: false`；本 Track 无 compose、无镜像）
- [ ] `manifest.stages` 覆盖所有 `stages/*/ticket.yaml`（六个阶段目录 + board-only 的 `stage-00-onboarding`）
- [ ] `mentor_policy.may_write` 与 `files_to_change` 不相交（六张卡均为 `[]`）
- [ ] 分支链只加不删；`-sol` 从同阶段 base 切出（命令序列见 §3；helper 冻结策略见 §3 与 §7）
- [ ] 全部判据可在学员本机**离线**复现：不联网、不下载 jar/agent、不需要 docker、不依赖特定硬件型号
