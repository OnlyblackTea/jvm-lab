# JVM 内存与 GC 八股 · Track 设计规格

> 状态：设计稿（未开工）· 对应平台契约见 [`_CONTRACT.md`](./_CONTRACT.md)
> 一句话定位：给「背得出 GC 分代、却从没亲眼见过 OOM」的 Java 后端——在一个**故意会跑挂**的服务里，
> 把三类 OOM、类加载器泄漏、对象生命周期都用**本机可复现、可断言的证据**走一遍。

**卖点（三条以内）**

1. **OOM 是做成「必然」的，不是碰运气**：子 JVM 一律用**固定的 `-Xmx`/`-XX:MaxMetaspaceSize`/`-XX:MaxDirectMemorySize`**
   起，工作负载与对象大小也是固定的——「这把一定炸」由算术保证，跟机器快慢无关。
2. **判据是可观测结构，不是毫秒数**：GC 停顿的毫秒、JIT 生效的时机、吞吐百分比**一律不进 canonical 测试**；
   进测试的是「GC 日志里出现了哪类停顿」「某个类加载器有没有被卸载」「堆转储里某类的实例数是否超过界」。
3. **每一步都有对照实验**：同一份代码在「开着 vs 关着某个 JVM 开关」下的**结构差异**就是判据，
   学员交卷时手里天然有一组 before/after 证据，而不是一句「我加了个参数」。

### 1.1 总原则：本 Track 的判据长什么样

本 Track 不判「快不快」，只判五种**结构事实**，每一种都在学员本机离线可得：

| 判据形态 | 怎么拿 | 为什么不怕抖动 |
|---|---|---|
| **进程级结局**：子 JVM 是「跑完了并打出收尾标记」还是「带着某类 OOM 死了」 | canonical 测试用 `ProcessBuilder` 起子 JVM，读退出码 + 子进程自己写出的结构化 stdout 标记 | 结局是二值的；OOM 由固定内存上限 + 固定存活集算术保证，不靠时序 |
| **JVM 自带计数器/MXBean**：已加载类数（`ClassLoadingMXBean`）、池内缓冲区总容量（`BufferPoolMXBean`）、堆/元空间 used（`MemoryMXBean` + `MemoryPoolMXBean`） | 子 JVM 自己在关键点采样并打印；需要时先 `System.gc()` 再用**有界轮询**读 | 计数器是单调量或退出前的稳态量，与墙上时间无关 |
| **GC 日志的结构**（不是时长） | `-Xlog:gc*:file=...`，测试按行做正则：出现的是 `Pause Young` 还是 `Pause Full`、有没有 `[gc,phases]`、行格式是否可解析 | 只匹配「事件类型与格式」，不匹配任何毫秒/字节数值 |
| **离散计数与口径对账**（v1.1 新增） | 排空后的驻留条数、被拒批次数、在途租约容量、已定义类数、交接口径差额（`OFFERED == DELIVERED + REJECTED`）——子 JVM 自己在关键点采样并打印 `KEY=VALUE`；测试只做整数相等 / 整数上界断言 | 计数要么是**单调量**、要么是**退出前的稳态量**；差额是「两个整数相减」，不存在「接近 0」这种模糊判定 |
| **确定性序列的失败路径**（v1.1 新增，全 Track 只有两处，已点名） | 测试按固定顺序直接调 API（借一块 → 注入一次转运失败 → 收尾采样；或灌到容量上界再灌一批），重复跑结论完全一致 | 现象本来就是「顺序做出来的」，不靠竞态碰运气；两处都不进冒烟、也不影响各自的单线程基线（论证见 §1.2 与 §2.4） |

> 上表第 4、5 行是 v1.1 扩面新增的判据形态。扩面加的是**文件数、缺陷族数与边界路径数**，
> 不是「更多不稳定的现象」——这条纪律在本轮没有被破坏：新增判据没有一条依赖毫秒数或编译时机。

> [!IMPORTANT]
> 「固定参数让结论稳定」是本 Track 的**唯一**确定性来源。所有 canonical 测试都通过一个受保护的
> 测试 helper 起子 JVM，参数来自一个**受保护的、进判定面的固定参数文件**（`src/test/resources/jvmflags/*.flags`）。
> 学员改不到它，平台体检时也不必信任学员机器上的默认 GC/堆配置。

**红为什么「红在对的地方」**（这一条是判别性门的核心，逐条排除常见的「假红」）：

- **不是编译错**：19 处改动面文件在骨架上都编译通过、每个包的正常路径（记录入队 → 处理 → 汇总；编译 → 自检 → 替换；
  借 → 转运 → 归还；加载 → 校验 → 换代；留档 → 排空 → 汇总；解析 → 归并 → 交付）都能跑通，
  红的全部是**资源上限撞墙**、**失败路径漏账**或**证据缺失**。
- **不是脚本为空**：每个 canonical 测试都跑真实负载并断言子进程的结构化输出，断言失败信息里带子进程原始 stdout/stderr。
- **不是装配失败**：本 Track 没有外部基础设施，没有 Spring 上下文、没有端口、没有镜像——「环境没起来」这种红在物理上不可能。
- **不是永远红**：`stage-NN-<name>-sol` 分支上六个 stage 全绿（准入门的另一半就是这样验的）。
- **红在缺陷的因果链上**：每一条红都能一句话说清「因为 X 保留了不该保留的引用 ⇒ 固定上限 Y 被撞穿」，
  或者「因为 X 只在成功路径上做了归还 ⇒ 失败路径的那一块永远不回来」。
  参数不是判据，**接线才是判据**——学员把 `-Xmx` 调大也不会变绿，因为子 JVM 的参数是受保护的固定文件。
- **（v1.1）每条新增红都能摘出来单独看**：14 条红每一条都单独起一个子 JVM、只断言**它自己那条不变量**，
  因此「修好一处却让另一处变红」在报告里是可分辨的。最容易误判的一处是 Stage 5：它的两条红分属
  「存活集形状」（与 JIT 耦合）与「窗口驻留生命周期」（纯计数），规格要求它们**不共用同一次子 JVM 运行**，
  免得第二条的驻留量污染第一条的对照差——这条约束写进了 §4 Ticket 5 的 `expect`。
- **（v1.1）两处「单线程可见」的形态已点名类别**：`TransferService.transfer` 的失败路径漏归还
  （**确定性序列复现的逻辑缺陷**）与 `ProfileService.deliver` 的静默丢弃（**资源上限被击穿才暴露**）。
  前者按 §1.1 第 3 条用确定性序列复现、且不碰冒烟与单线程基线；后者在容量内根本不触发。
  两处都在 §2.4 的缺陷表、§4 对应 ticket 的题面与 `expect` 里写明了类别，**不要让读者以为它们是竞态**。

### 1.3 确定性论证（为什么多次跑结果一致）

1. **上限固定**：堆 / 元空间 / 直接内存三个上限都写死在受保护的 `.flags` 文件里，不由学员机器决定。
2. **工作负载固定**：每条负载的条数、每条记录的对象大小都是常量（如 100000 条 × 4096B 的 `byte[]`），
   于是「存活集最小可能值」是一个能算出来的常数。
3. **结论由算术保证**：只要「存活集最小可能值 > 上限 − 启动开销 − GC 余量」，OOM 就必然发生；
   反过来，修复后「存活集上界 + 收尾预算 < 上限」也必然成立。两侧都留了 ≥2 倍余量。
4. **子进程自述状态**：结论不靠解析易变的 stderr 文案，而靠子 JVM 自己打印的 `KEY=VALUE` 标记
   （`GATE=`、`OOM=`、`PROCESSED=`、`CLASSES_AFTER_GC=`、`POOL_CAPACITY_AFTER_CLOSE=`……）；
   即便日后 JDK 补丁改了 OOM 文案，测试也只把文案当**补充证据**，判定仍落在标记上。
5. **类卸载用有界重试**：`System.gc()` + 轮询 `ClassLoadingMXBean`（上限 10 次 / 每次 200ms），
   而不是依赖「某一刻恰好卸载了」；轮询次数的目的是把 flaky 概率压到可控，不构成时间阈值判据。
6. **JDK 一致性前置断言**：每个 canonical 测试开头断言「本机 `java.version` 主版本 = 17 且
   `java.vm.name` 含 HotSpot」，不满足就**响亮失败**并提示去看 `docs/架构与约定.md` 的版本约定——
   宁可说「环境不可判定」，也不给一个静默通过的绿。
7. **把「编译层级」这个自由度关掉**：所有子 JVM 的 `.flags` 里都写死 `-XX:-TieredCompilation`
   （只留 C1/C2 的确定一档），因为分层编译的层数取决于编译线程数与机器核数，
   会让 Stage 5 那种「对照差」在快机器和慢机器上落在不同的数量级上。这一条是本 Track 里
   「怎么把抖动量确定化」最实在的一招：**不是把阈值放宽，而是把产生差异的自由度删掉**。
8. **（v1.1）新增判据全部落在离散计数上**：排空后的驻留条数（`QUEUE_RETAINED_AFTER_DRAIN`、
   `PROFILE_RETAINED_AFTER_DRAIN`）、峰值驻留（`QUEUE_RETAINED_PEAK`、`PROFILE_RETAINED_PEAK`、
   `ANALYSIS_RESIDENT_RECORDS`）、拒绝次数（`QUEUE_REJECTED`）、口径差额（`OFFERED - DELIVERED - REJECTED`）、
   在途租约容量（`LEASES_OUTSTANDING_CAPACITY`）、规则身份取值个数（`RULE_KIND`）。
   这些量的**上界与容量都写在受保护的 `jvmlab.properties` 与 `.flags` 里**，不由学员机器决定，
   所以「有界」是一条能复算的整数不等式，而不是一句体感。
9. **（v1.1）「排空后归零」用一次显式排空 + 一次采样**，不做轮询、不等 GC：`drain()` 是同步方法，
   返回后立刻读计数器，因此结论与 GC 时机无关。这一条把「只借不还」这类缺陷从「要看 GC 脸色」
   变成了「读一个整数」——确定性来自**接口本身是同步的**，不是来自等得久一点。
10. **（v1.1）失败路径的确定性由「注入式故障」保证**：Stage 3 的转运失败不是靠超时或概率触发，
    而是 `TransferService` 上一个显式的失败注入点（`failNextTransfer()`），按固定顺序调用即可复现；
    重复跑 100% 稳定。它在骨架上**不影响成功路径**，所以单线程基线与冒烟都不受牵连。

## 2. 骨架仓设计

### 2.1 边界声明（先划清，避免两条 Track 重叠）

本 Track 只讲**内存与 GC**：

- ✅ 讲：堆 / 元空间 / 直接内存三个区域、OOM 三类、堆转储、GC 日志结构、类加载与卸载、对象生命周期（逃逸/标量替换）。
- ❌ **不讲**（归 `concurrency-lab`）：JMM、`volatile`、`synchronized` 与锁消除、`happens-before`、线程池、
  `ThreadLocal` 语义、CAS/原子类。骨架里**故意不出现**任何并发原语，免得两条 Track 的考点互相串味。
  （Stage 5 的对照实验只用单线程循环与 JVM 开关，不引入任何锁或内存序问题。）
- **Stage 5 为什么在边界内**：它讲的是「对象的分配与消除」——分配压力直接决定新生代回收频率，
  是本 Track 主线的收尾（一个对象活多久、要不要上堆）。它**只**做逃逸分析/标量替换这一件事，
  观察手段也限定在「堆的存活集形状」，不碰编译器的 IR、也不碰锁。若评审认为 JIT 面太宽，
  裁掉整条 Stage 5 是安全的：它是链尾前的选修性延伸（Stage 6 用不到它的结论），
  但**不要**把它拆成"锁消除/编译优化"混进别的阶段——那正是这两条 Track 会重叠的地方。
- **（v1.1）Stage 5 扩面后仍然在边界内**：扩面给它加的第二条不变量（留档窗口的驻留生命周期：
  有界、排空归零、排空不丢）是**对象生命周期**这一考点本身，与 JIT 无关、与并发无关；
  它反而把这条边界钉得更清楚——**只有一条判据与 JIT 耦合**，其余全是离散计数。
  规格同时保留了 `_SCALE.md` §2 的退路（见 §1 的「Stage 5 的取舍」与 §7 的风险表）：
  若这条门落地时确实撑不住下限或撑不住稳定，就与 Stage 6 合并成 5 个 stage，而不是给它继续加压。

### 2.3 分层与约定

- **没有 Spring、没有容器、没有数据库**。`JvmLabApplication.main(args[0])` 按负载名跑一段固定工作，
  `System.exit(0)` 正常收尾；任何 OOM 都在 `main` 的兜底里被**捕获 + 落成标记 + 退出**，
  这样「OOM」本身变成一条可断言的 stdout 记录，而不是一段易变的 stderr 文案。
- **待机记录（emergency record）**：`main` 启动时预分配一小块 `byte[]` 和一个预格式化的行缓冲，
  OOM 处理器只用这块内存把标记写进 `FileDescriptor.err` 再 flush——元空间耗尽时堆是空的，
  这个设计让「濒死打印」几乎不可能失败，判据因此稳定。
- **负载参数集中**：条数、每条的 payload 大小、循环次数全在 `jvmlab.properties` 里，代码只读它。
  这样「OOM 的算术」是文档化的常数，而不是散落在代码里的魔数。
- **`pom.xml` 的 surefire 必须写成确定形态**：`forkCount=1`、`reuseForks=false`、
  `parallel` 关闭、`argLine` 为空（**不要**在 surefire 的 JVM 上设堆上限——那会让「测试自己也需要内存」
  与「被测子 JVM 的上限」两件事混在一起），`-Dfile.encoding=UTF-8`、`-Duser.language=zh -Duser.country=CN`。
  子 JVM 的内存参数**只**来自 `.flags` 文件，测试 JVM 的参数不参与任何判据。
- **JVM 参数集中**：所有子 JVM 参数都在 `src/test/resources/jvmflags/*.flags` 里，`JvmRunner` 逐行读取并与
  `JvmFlags` 里的白名单求交——**学员无法在执行期改上限**，他只能改接线。
- **`HprofReader` 是「最小可用」的**：只解析 HPROF 的 `UTF8` / `LOAD_CLASS` / `STRING` / `INSTANCE_DUMP`
  四类记录，产出「类名 → 实例数 / 浅堆字节」。它**不做**支配树与 retained size，
  所以 Stage 6 的判据用「实例数 + 浅堆」这两个它真能给准的量（见 §1.4）。
- **（v1.1）每个 stage 的三个角色是三个不同的类，职责写进接口注释**。这样做的理由是 `_SCALE.md` §1 的
  第一句：一个 stage 应当像一次真实的代码评审——改动面跨了组件，学员才需要理解「它们怎么咬合」。
  三类角色的分工在本 Track 里固定为：① 核心状态/算法（决定「对不对」）② 内存语义载体（决定「留不留得住」）
  ③ 调用编排与异常·边界（决定「失败与满载时怎么办」）。三者的接口签名在骨架里冻结，只留实现语义是错的。
- **（v1.1）两张登记表**：`rule/RuleDefinitionRegistry`（**类定义**的登记：谁被定义了、何时可以走）
  与 `rule/LoaderScope`（**加载器**的生命周期：创建、换代、销号）刻意分成两个类，**不要合并**——
  Stage 2 判「元数据有界」，Stage 4 判「类身份与卸载」，合并后一条红会顺带把另一条带绿或带红，
  §1.2「每个 stage 只在自己那几条考点上红」的前提就没了。同理，`buffer/SnapshotQueue`（暂存容量与排空）
  与 `profile/ProfileWindow`（留档驻留）也是两处不同语义的有界容器，各有自己的上界常量。
- **（v1.1）固定上界都写进 `jvmlab.properties`**：`snapshot.queue.capacity=4096`、
  `profile.window.capacity=2048`、`dump.index.resident.limit=4096`（等于应用类数上界）、
  以及各负载的条数与每条的 payload 大小。判据里的「有界」断言全部引用这些常量，
  学员改不到它们（在判定面里）；**冒烟负载的规模一律低于这些上界**（见 §2.6），
  这是「扩面不得让冒烟变红」这条约束在算术上的落点。
- **（v1.1）`diagnosis/` 必须自己读转储**：Stage 6 学员的分析器**不许**调用判定面的 `diag/HprofReader`
  去拿答案（那等于抄判据的尺子），它只能自己按 HPROF 的记录格式聚合。判据因此是「两边独立算、
  再比对」，而不是「自己跟自己比」——这条约定写进 `docs/架构与约定.md`，并由 Ticket 6 的题面点明。
- **（v1.1）失败注入点是显式的**：`TransferService.failNextTransfer()` 只影响**下一次**转运，
  是 `_SCALE.md` §1.1 第 3 条所说的「确定性序列」的载体。它不在任何正常路径上被调用，
  因此冒烟与单线程基线都不受它影响；这条约定同样写进 `docs/架构与约定.md`。

### 2.6 冒烟测试

`src/test/java/com/devteam/jvmlab/smoke/SmokeTest.java`，`@Tag("stage00")`：

- 断言 `java.version` 主版本 = 17、`java.vm.name` 含 HotSpot；
- 断言 `jvmlab.properties` 能读到、`JvmFlags.load()` 能读到全部 `.flags` 文件（含 `stage00-smoke.flags`）；
- 断言 `JvmLabApplication.main` 在**冒烟参数**（`-Xmx512m`、只跑 1000 条）下能 `GATE=headroom-ok` 收尾；
- **（v1.1）断言每条正常路径都能被走完一次**：记录入队 → 交接 → 汇总；编译 → 自检 → 替换 → 注销；
  借 → 转运 → 归还；加载 → 校验 → 换代；留档 → 排空 → 汇总；解析 → 归并 → 候选过滤。
  它只断言「跑完了、没有异常、收尾标记正确」，**不断言任何内存上界**。

它在骨架上**天生是绿的**——所以它只进 `manifest.stages` 的看板与体检，不出 ticket、不要分支
（理由同 `_CONTRACT.md` §5 对 `stage-00-onboarding` 的处理）。

**（v1.1）扩面后冒烟为什么还是绿的（算术落点，`_SCALE.md` §1.1 第 1 条）**：冒烟的固定负载规模
（1000 条记录 / 1000 轮校验 / 一次正常切换 / 1000 个 loader 以内）**全部低于**新增结构的固定上界——
暂存容量 `snapshot.queue.capacity=4096`、留档窗口 `profile.window.capacity=2048`、
记录索引上界 `dump.index.resident.limit=4096`；而 D-A / D-D 那种「单调增长」的缺陷在 1000 这个规模上
离撞上限还差一个数量级以上。至于两处「单线程可见」的缺陷：D-I 需要显式调用失败注入点（冒烟不调），
D-C 需要灌到容量上界才触发（冒烟只灌 1000 条）。**结论：13 处新增文件的存在不会让 `stage00` 变红。**
这一条是扩面的硬前提，落地时必须先跑 `mvn test -Dgroups=stage00` 再提交（§8 已列为勾选项）。

### Ticket 1 · `jvm-stage-01`

```yaml
identity:
  id: jvm-stage-01
  schema_version: 1
  ticket_version: 2
  stage: 1
  title: 堆里的入住名单

brief:
  problem: |
    ## 问题背景

    【线上问题｜来自：稳定性看板 · 优先级 P0】网关的重试巡检服务每隔一段时间挂一次，
    每次都是同一个形状：启动时一切正常，跑着跑着老年代占用只涨不跌，Full GC 越来越密，
    最后整个进程消失，只留下监控归档里的一份堆转储。值班同学把内存调大过一轮，
    症状只是推迟了几小时；看过日志的人都说「GC 一直在干活」，于是没人再往下查。

    这个服务在本机可以完整复现，而且不需要你等几小时：它以一组固定的内存参数启动，
    内存一旦不够就自己把当时的内存快照写出来并退出。你要做的是让它在同样的内存额度下
    跑完同样的工作量。

    ## 问题表现

    巡检服务的每个检查周期都会把这一轮的订单快照交出去留档，这是「看板要能回放」的需求，
    没人觉得有问题。可留档这件事在内存上有个不易察觉的性质：交出去的东西只要还有人在引用，
    GC 就一个新对象都收不回来。于是每一轮都往同一个地方塞一批快照，越塞越多，
    直到某一次新对象真的分配不出来为止。

    症状表面上像「GC 不干活」，实际恰好相反——GC 每次都尽力了，只是它面对的是一份只增不减的
    名单：能被回收的对象几乎没有，于是每次回收的收益趋近于零，频率自然越来越高。
    这也是为什么调大内存只是把爆炸推迟，而不是解决问题。

    同一条巡检链路上还有两个症状，方向与上面不同，值班同学一开始把它们当成同一件事。第一个是
    「排空之后账还在」：看板上有一个「当前暂存了多少条快照」的读数，批次明明已经交给下游了，
    这个数却不回落，于是它随运行时间单调爬升，永远是一条斜线。第二个是「盘点对不上」：夜里有一条
    告警说交接总数比产生的总数少了几批，可日志里一条报错都没有——被少掉的那几批，恰恰是暂存区
    已经装满的时候交进来的。

    ## 你需要完成的修改

    本题需要修改以下三个文件（`scope.files_to_change`），它们分别承担三个角色：

    - `src/main/java/com/devteam/jvmlab/buffer/BufferPool.java`：**核心状态/算法**，承担「接收这一轮的
      快照并交给下游」的职责。现在它在交接之后仍然把快照留在自己手里，你要让它在交接完成后不再持有
      这些对象。
    - `src/main/java/com/devteam/jvmlab/buffer/SnapshotQueue.java`：**内存语义载体**，是这两者之间的
      有界暂存区，同时对外提供「当前暂存了多少条」这个读数。它现在给出的是「历史交接条数」，
      你要让它变成「此刻真的还留在暂存区里的条数」：排空之后回到零，全程不超过约定容量。
    - `src/main/java/com/devteam/jvmlab/profile/ProfileService.java`：**调用编排与异常·边界路径**，
      是「接收一批 → 交给下游 → 汇总」的唯一落点。暂存区满时它确实会拒绝新批次，这一点是对的；
```

```yaml
    第二反应是「那就把堆调大」，结果两次都没用。

    这个模块做的是数据的零拷贝转运：为了避免反复在堆里搬运大块数据，它用堆外的缓冲区
    来承载流量。堆外内存不在堆容量里，所以堆上的指标**结构上就看不到它**。

    ## 问题表现

    这套缓冲区的分配与释放是分开的两件事：拿到一块缓冲区很容易，把它还回去需要显式动作。
    骨架里前一半写好了、后一半没有接上——用完的缓冲区既没有被标记为可回收，
    也没有在模块收尾时统一处理。于是每次转运都在账上多留一块。

    更隐蔽的一点是：这些堆外缓冲区的回收**依赖 GC 顺手去做**。而在堆里毫无压力的情况下，
    GC 本来就不需要跑——不跑就没人去回收，回收不了就继续欠账，欠到最后由操作系统来执行死刑，
    于是你看到的是「进程被杀」而不是「OOM 异常」。

    同一套转运链路还有两个症状，方向各自不同。第一个是「一次转运就顶穿额度」：白天有一条大流量
    通道一次要同时铺开若干块缓冲区，配的额度本来只够其中一部分，可系统照样全部批准，随后是一次
    集中爆掉——每一块单看都不大，问题出在「同时拿在手里的总量」从来没被算过。第二个更难查：
    夜里有一条通道读到一半上游断了，那次转运失败之后，监控上的「在途堆外容量」就再也没有回到
    失败前的水位——失败是偶发的，欠账却是永久的。
```

## Stage 1 · 堆 OOM 与堆转储 ⬜

**亲手场景**：巡检服务的快照被静态名单一直持有 → 暂存区排空之后账还不回落 → 装满时批次被悄悄丢掉 → 你用固定额度与三个计数把这件事说清。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 运行时内存区域 | 堆(线程共享,对象)/虚拟机栈(私有,栈帧)/元空间(类元数据)/直接内存(NIO) | JVM 运行时数据区都有哪些？哪些线程共享？ |
| 可达性分析 | 从 GC Roots 出发可达即存活；GC Roots 含栈帧局部变量、静态字段、常量、JNI 引用 | 如何判断一个对象可以被回收？为什么不用引用计数？ |
| 分代假设 | 绝大多数对象朝生夕灭 ⇒ 新生代频繁小回收、老年代少见整体回收 | 为什么分代？对象什么时候进老年代？ |
| 分配与 OOM 的关系 | 分配失败前先触发回收；回收后仍不够才抛 OOM ⇒ 「GC 很勤」与「内存不够」可以同时成立 | 为什么 Full GC 频繁不代表 GC 有问题？ |
| 堆转储 | `HeapDumpOnOutOfMemoryError` 或手动命令导出全部对象图，是「谁占着内存」的直接证据 | 线上怎么拿到并分析堆转储？ |
| 直方图 vs 堆转储 | 直方图只有类与数量/占用（轻），堆转储有引用路径（重） | jmap -histo 和 dump 各自什么时候用？ |
| 有界暂存与背压 | 暂存容量是资源上限：满了要么拒、要么让上游等，不能悄悄扩、也不能悄悄丢 | 队列满了该丢最新的还是最旧的？为什么不能静默丢？ |
| 拒绝路径的可观测性 | 「被拒」必须是可计数、可核对的事实，否则容量耗尽会伪装成「一切正常」 | 为什么要统计被拒绝的请求数？ |
| 交接口径对账 | 产生的总量 = 交接的总量 + 被拒的总量；差额就是「静默丢失」的直接证据 | 你怎么证明中间环节没丢数据？ |

**复现命令**：
```bash
java -Xmx256m -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=target/gc-evidence/ \
     -cp target/classes com.devteam.jvmlab.JvmLabApplication heap-oom
```

## Stage 2 · Metaspace OOM 与类卸载 ⬜

**亲手场景**：规则每编译一批就多留一套加载器 → 同一份规则被反复定义 → 释放之后元数据仍不回落。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| Metaspace vs 永久代 | JDK 8 起类元数据移到本地内存的 Metaspace，默认不限但可设上限 | Metaspace 和永久代有什么区别？会 OOM 吗？ |
| 类元数据的归属 | 类的元数据挂在「定义它的类加载器」上，loader 存活则类不可卸载 | 一个类什么时候可以被卸载？ |
| 类卸载条件 | 该类所有实例已回收 + 定义它的 loader 已回收 + 对应的 Class 对象无引用 | 满足什么条件类才会被卸载？ |
| 运行期生成类 | 动态代理/字节码生成会持续产生新类，缓存键设计不当就会重复定义 | 动态代理为什么会把 Metaspace 撑爆？ |
| 溢出归宿 | 元数据不足抛 `OutOfMemoryError: Metaspace`，堆转储里看不到原因 | 报 Metaspace OOM 该怎么查？ |
| 定义登记与注销 | 「谁定义过这个类」是一份显式的账；只登记不注销，等于把生命周期拉成无限 | 类加载器缓存的正确失效方式是什么？ |
| 动态类的幂等性 | 同一份输入重复编译应当复用同一个类定义，判等依据是内容而不是对象身份 | 动态代理缓存为什么要按内容做键？ |

**复现命令**：
```bash
java -XX:MaxMetaspaceSize=64m -Xlog:class+load=info,class+unload=info:file=target/gc-evidence/classes.log \
     -cp target/classes com.devteam.jvmlab.JvmLabApplication metaspace
```

## Stage 3 · 直接内存 OOM 与缓冲区 ⬜

**亲手场景**：零拷贝转运的堆外缓冲区只借不还 → 一次批量取用顶穿额度 → 转运失败之后账目再也不回落 → 你用池计数器把账算清。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 直接内存 | `allocateDirect` 在堆外分配，不在堆上限内，由 `MaxDirectMemorySize` 约束 | 直接内存属于 JVM 哪块区域？受哪个参数限制？ |
| Cleaner 回收时机 | 堆外内存由虚引用 + Cleaner 在 GC 时释放，堆无压力则迟迟不释放 | 直接内存什么时候释放？为什么它会泄漏？ |
| 失败信号 | 预留失败抛带「Cannot reserve」字样的 OOM，或进程被系统 OOM Killer 干掉 | 堆外内存溢出和进程被杀怎么区分？ |
| 可观测手段 | `BufferPoolMXBean` 按类型给出容量与已用，堆外池在 `MemoryPoolMXBean` 里单独一档 | 怎么监控堆外内存？ |
| 堆内存泄漏 vs 堆外泄漏 | 前者堆转储可查，后者要在池计数器与本机进程视角上看 | 堆没涨但内存一直涨，怎么排查？ |
| 租约与在途额度 | 额度约束的是「同时持有的总量」，不是单次申请的那一块有多大 | 池化资源怎么防止超额分配？ |
| 失败路径的资源归还 | 借出的资源必须在**所有**出口归还；「只在成功时归还」是一半的实现 | 为什么资源释放要放在 finally 里？ |
| 确定性序列复现 | 按固定顺序调 API 就能 100% 复现的缺陷，是逻辑缺陷而不是竞态 | 怎么判断一个 bug 是竞态还是逻辑错？ |

**复现命令**：
```bash
java -XX:MaxDirectMemorySize=64m -cp target/classes \
     com.devteam.jvmlab.JvmLabApplication direct-memory
```

## Stage 4 · 类加载与双亲委派 ⬜

**亲手场景**：热更新用自定义加载器却绕过了委派 → 同名类出现两份 + loader 被登记表握住 → 元数据不回落。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 类加载过程 | 加载 → 验证 → 准备 → 解析 → 初始化；`loadClass` 默认先委派父加载器 | 描述类的生命周期 |
| 双亲委派 | 先父后子，保证核心类不被替换、同名类只被定义一次 | 为什么需要双亲委派？怎么打破？ |
| 打破委派的场景 | SPI/模块化、热部署与隔离、字节码框架都需要绕过或改写委派 | 哪些框架打破了双亲委派？为什么？ |
| 类加载器泄漏 | 静态表、线程上下文、ThreadLocal 都会隐式持有 loader，进而钉住它定义的类 | 类加载器泄漏的典型原因？ |
| 类的唯一性 | 全限定名 + 定义它的加载器共同决定类的身份，「同名不同类」会引发 `ClassCastException` | 同一个类为什么会出现两份？ |
| 加载器作用域的生命周期 | 作用域要有明确的创建、切换与销号，否则它钉住的那些类一个都走不了 | 热部署为什么要成对地管加载器？ |
| 隔离与统一的边界 | 框架类型统一由上级提供、业务同名类各自隔离；边界划错，两边都会坏 | 什么时候需要打破双亲委派？ |

**复现命令**：
```bash
java -Xlog:class+load=info,class+unload=info:file=target/gc-evidence/reload.log \
     -cp target/classes com.devteam.jvmlab.JvmLabApplication classloader
```

## Stage 5 · 对象生命周期与逃逸分析 ⬜

**亲手场景**：校验上下文被交给留档模块 → 短命对象全都上堆 → 你把作用范围收回来，用对照实验证明差别。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 对象分配 | 优先在 TLAB 上分配；逃逸分析结论不同会改变分配与消除策略 | 对象一定分配在堆上吗？ |
| 逃逸分析 | 分析对象的作用范围（不逃逸/方法逃逸/线程逃逸），是后续优化的前提 | 逃逸分析在分析什么？ |
| 标量替换 | 不逃逸的对象可拆成字段直接放在栈/寄存器，省掉堆分配 | 什么是标量替换？什么条件下发生？ |
| 分配压力 | 分配速率决定新生代回收频率；消除短命对象能直接削弱分配压力 | 怎么降低 GC 频率？ |
| 可观测的边界 | 编译器内部决策没有稳定外部接口，只能靠对照实验与计数器间接观察 | 你怎么证明 JIT 优化生效了？ |
| 留档窗口的驻留生命周期 | 留档留在内存里的那部分必须有上界，并在排空后归零；排空不许丢记录 | 缓冲区什么时候该清空，而不是继续追加？ |
| 判据的抖动边界 | 编译时机、停顿毫秒数只能「可观测」；能进判据的是离散计数与结构差 | 哪些性能数字不能拿来做验收标准？ |

**复现命令**：
```bash
java -Xmx256m -XX:+DoEscapeAnalysis -cp target/classes \
     com.devteam.jvmlab.JvmLabApplication escape-on
java -Xmx256m -XX:-DoEscapeAnalysis -cp target/classes \
     com.devteam.jvmlab.JvmLabApplication escape-off
```

## Stage 6（选修）· 堆转储实战诊断 ⬜

**亲手场景**：只有一份别人留下的、没有崩溃现场的堆转储 → 你交出「数量第一名与占用第一名」两张表。

| 考点 | 一句话原理 | 面试题 |
|------|-----------|--------|
| 转储读取 | HPROF 里 `LOAD_CLASS` + `INSTANCE_DUMP` 就能给出「类 → 实例数/浅堆」 | 堆转储里都有什么？ |
| 直方图口径 | 实例数与浅堆好算；保留集要支配树，口径差异大 | 浅堆、深堆、保留集分别是什么？ |
| 数量 vs 占用 | 「很多小对象」与「少数大对象」是两类不同的病，两张排序表要一起看 | 你排查内存问题先看哪个排序？ |
| 引用链 | 从 GC 根到对象的引用链回答「为什么它还活着」，是收尾动作而非第一步 | 怎么找内存泄漏的根源？ |
| 泄漏 vs 高水位 | 泄漏是单调不可回落的量，高水位是可回落但设得高 | 内存缓慢上涨一定是泄漏吗？ |
| 结论表达 | 诊断的产物是可核对的事实 + 排除依据，不是工具输出截图 | 复盘会上你怎么讲清内存问题？ |
| 流式聚合 | 大转储必须一趟读完就聚合：驻留量只允许是聚合结果，不能随输入线性增长 | 怎么分析比内存还大的堆转储？ |
| 候选过滤的口径 | 「应用类」的边界（排除 JDK、工具类型与基础类型数组）决定了排序结果是否有意义 | 为什么直方图第一名常常是数组？ |
| 无候选的显式报告 | 过滤之后没有候选是一个合法结论，必须显式说出来，而不是交一张空表 | 排查不出结论时该怎么交付？ |

## 7. 风险、妥协与工作量

| 风险 | 影响 | 缓解 |
|---|---|---|
| **OOM 不必然**（负载量级不够、机器 JVM 启动开销差异） | Stage 1/2/3 的判别性门会变成 flaky，甚至「骨架也绿」 | 每个上限后的存活集都留 ≥2 倍余量；子进程用**固定参数文件**起；负载参数集中在一处便于调；准入校验必须在**同一台机器**上同时验骨架红与 `-sol` 绿 |
| **`HprofReader` 解析口径漂移**（不同 JDK 的 HPROF 记录微调） | Stage 1/6 的直方图断言失准 | 只解析四个稳定记录类型；判据用「实例数 + 浅堆」并给容差；每个 canonical 测试前置断言 JDK 主版本 |
| **共享 helper 改动破坏「只加不删」链** | 后续阶段分支合并时会引入非本阶段内容 | helper 在 Stage 1 一次性落地并冻结；任何 helper 改动都要重跑全部阶段判别性校验（列为发布前必做项） |
| **子进程挂死**（GC 抖动或死循环） | CI/本地跑测试可能长时间不返回 | `JvmRunner` 统一设置超时（120s）并在超时后强杀，超时**判定为失败**而非跳过 |
| **`jcmd`/`jmap` 在受限环境不可用** | Stage 1/2/4 的附加证据拿不到 | 判据的全部硬门都走 `ProcessBuilder` + stdout 标记 + MXBean，`jcmd`/`jmap` 只用于"人自己看"的证据；`DiagnosticTools` 拿不到就明确报「本机不可用」，绝不静默通过 |
| **Stage 5 与 JIT 实现细节强耦合** | 未来 JDK 改变逃逸分析行为会让判据失效 | 判据用「开/关开关的对照差」而不是绝对阈值；**子 JVM 一律加 `-XX:-TieredCompilation`（受保护的 `.flags` 里写死）**，让「编译层级」这个自由度消失，否则同一个断言会因为机器核数与编译线程抢占而不稳定；在 `docs/架构与约定.md` 里钉住已验证的 JDK 发行版；把该门标注为**最脆弱的一门**。**（v1.1）**扩面时**没有**给它加任何与编译时机/层数相关的判据，新增的那条红是纯离散计数且独立起子 JVM（见下方新增行） |
| **（v1.1）Stage 5 的两条红互相污染** | 留档窗口的驻留量会让 `PEAK_HEAP_USED_AFTER_GC` 的对照差失真，两条判据一起变得不可解释 | 规格**硬性要求这两条红不共用同一次子 JVM 运行**（各自 `ProcessBuilder` 一次），写进 §1 的 v1.1 块与 Ticket 5 的 `expect`。**退路**：若落地实测仍不稳，按 `_SCALE.md` §2 与 Stage 6 合并成 5 个 stage（`stage-05-lifecycle-and-dump`，依赖 `jvm-stage-04`），并重算六条 `bagu_map_ref` |
| **（v1.1）扩面新增的 13 个类本身写错（单线程路径就不对）** | 冒烟 `stage00` 或本阶段的单线程基线会变红，破坏「骨架功能是通的」这条第一原则（`_SCALE.md` §1.1 第 1 条） | 每个新增类交付前必须先跑 `mvn test -Dgroups=stage00` + 上一级的全部基线；又因为它们的缺陷在冒烟规模下**不发生**（§2.6 的算术），这条门是二值且可在提交前机械核对的 |
| **（v1.1）`diag/`（判定面）与 `diagnosis/`（改动面）混淆** | `protected_paths` 写错一个字母就是静默漏洞（`_CONTRACT.md` §4），或者把学员的改动面包进了判定面、让学员一动就判失败 | §2.2 的目录树、§2.2 的分界句、§6 的「新增文件归属」三处同时点名这对包名；准入门自查里单列一条核对 |
| **（v1.1）新判据需要 helper 产出更多计数器** | `JvmRunner` / `Evidence` / `JvmFlags` 一旦改动，就会波及全部六个阶段的既有结论 | 计数器全部复用现有的 `KEY=VALUE` 机制（`Evidence` 只解析、不认识具体键），新增的键在子进程侧打印即可；若确需改 helper，按本表第一行的老规矩重跑全部阶段判别性校验 |
| **（v1.1）Stage 6 的「驻留量」判据被夹具规模掩盖** | 夹具只有十几 MB，`ANALYSIS_RESIDENT_RECORDS` 在两个版本上可能都"看着不大" | 判据比的是**两个整数之间的关系**（驻留 ≤ 4096 而扫过 = 夹具记录总数），不是绝对内存量；夹具的记录条数因此必须足够多（≥ 30 万条 `INSTANCE_DUMP`），让"逐条留存"与"流式聚合"在计数上拉开数量级差 |
